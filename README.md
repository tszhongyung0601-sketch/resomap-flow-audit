# ResoMap 商家訂閱流程稽核

以商家身分實際走完 ResoMap「訂閱付款 → 語音上線」全流程，共 **21 個步驟**，逐步截圖記錄，並就流程本身指出問題與責任歸屬。

附錄另含一份 **Google Maps → OpenStreetMap 遷移評估**，依同一份實測流程列出所有 Google 觸點與遷移代價。

- **實測日期**：2026/08/26 – 08/27
- **測試景點**：香記烤鴨（台中市南區台中路 252 號）
- **後台**：`backend.resomap.app`（版本 `dev-1.0.0`）
- **線上閱讀**：https://tszhongyung0601-sketch.github.io/resomap-flow-audit/

> **關於截圖內容**：`evidence/` 為實測過程的原始截圖，除了帳號 Email 已塗銷之外未經修改。保留原樣是為了讓每一項發現都可被獨立查核。

## 一句話結論

**付費與交付之間，產品裡沒有任何一條路把它們接起來。**

商家買的是「3 個景點」的上架權，但付款完成的那一刻 App 沒有變化：沒有引導、沒有額度顯示、沒有「我的景點」入口。他必須自己回到地圖、自己打字搜尋店名、自己錄音、自己寫文案、自己拍照，再自己猜到右上角的三個點，最後靠自己反覆回訪去試「認領」按鈕能不能按。整條主線由三個純人工關卡串起來，而商家一個都看不到。

```
docs/                                  GitHub Pages 網站（線上閱讀入口）

  01-subscription-flow-audit.html      21 步實測全紀錄 + 問題清單與責任歸屬
  02-map-migration-assessment.html     Google Maps → OSM 遷移評估
deck/
  ResoMap-flow-audit.pptx              34 頁簡報（圖文對照，含地圖評估附錄）
evidence/
  第一步…第二十一步驟*.png/jpg          原始實測截圖 21 張（含後台 2 張）
build/
  deck.js                              簡報產生器（pptxgenjs）
  prep*.js                             截圖裁切／縮放腳本（sharp）
  pages.js                             把 reports/ 包成可獨立開啟的網頁並產生 docs/

```

`reports/*.html` 為獨立單檔，直接用瀏覽器開啟即可，支援淺色／深色主題。

## 重建簡報

```bash
npm install
node build/prep.js && node build/prep2.js && node build/prep3.js && node build/prep4.js
node build/deck.js
```

`prep*.js` 讀取 `evidence/` 的原始截圖，輸出到 `build/img/`；`deck.js` 讀 `build/img/` 產生 `.pptx`。
若 `build/img/` 已存在（本 repo 已含），可直接跑 `node build/deck.js`。

重建網站（`reports/` 改動後）：

```bash
node build/pages.js
```

> 註：`prep*.js` 目前寫死來源路徑為桌面的「商家訂閱流程2」資料夾。若要在別台機器重跑，需先把路徑改指到本 repo 的 `evidence/`。

## 問題清單（摘要）

完整清單見 `reports/01-subscription-flow-audit.html`。括號內為對應步驟編號。

### 一、工程實作缺陷 — 前端／後端／QA

| 嚴重度 | 問題 |
|---|---|
| 致命 | 按鈕可點但後端拒絕（18） |
| 致命 | 後台兩張表資料不一致：語音管理顯示已上架，景點管理顯示語音數量 0（19 ↔ 20） |
| 致命 | 上傳後沒有「審核中」狀態（16） |
| 嚴重 | Markdown 未解析，`##` 與 `**` 直接輸出（15） |
| 嚴重 | 自動續訂條款被容器裁斷（4）— 揭露義務問題，非排版瑕疵 |
| 嚴重 | 錯誤訊息不說原因也不說下一步（18、20b） |
| 待改 | 方案頁初始捲動位置錯誤（4）／「回復購買」幾乎不可見（4）／上傳檔名未清洗（11）／「取消認領」無二次確認（21）／營運後台掛 `dev-1.0.0` |

### 二、產品設計缺失 — PM／設計

| 嚴重度 | 問題 |
|---|---|
| 致命 | 付款成功後零引導（5 → 8） |
| 致命 | 訂閱綁帳號、內容綁景點，兩者在產品裡沒有連結 |
| 致命 | 「認領」這個步驟不該存在 |
| 嚴重 | 「點數」從未被定義也未被顯示／訂閱頁缺到期日、扣款日、取消入口／唯一商家入口藏在三個點裡（16）／「檢視認領中的景點」必定是空的／全程 0 則通知／商家與遊客共用同一套文案／金流分岔做成無防呆勾選框（12） |

### 三、流程與管理層 — 公司／專案管理

| 嚴重度 | 問題 |
|---|---|
| 致命 | 主線由三個純人工關卡串起來，商家全看不到 |
| 致命 | C 端被內部流程連坐（20b） |
| 致命 | 商業模式與產品交付互相矛盾——收 $3,800，內容 100% 由商家自己生產 |

## 附錄：Google Maps → OpenStreetMap（第二版）

完整評估見 `reports/02-map-migration-assessment.html`。
本版依「先列出前台實際操作、再逐步標記」的方法重做，取代第一版以「主鍵風險」為主軸的框架。

**結論：12 步裡只有 2 步真的碰到 Google。**

| | 步數 | 內容 |
|---|---|---|
| ResoMap 自己的 | **9** | 訂閱、圖片、文案、語音、送審、審核、認領、上架——換地圖服務動不到 |
| 依賴 Google | **2** | 搜尋店家、帶出店名與地址 |
| 目前不存在 | **1** | 建立景點／商家——換 OSM 後必須補上「搜不到 → 手動輸入 → 地圖選點」 |
| 前台無法確認 | 4 | 需工程師回覆 |

### 前台實測流程逐步標記

| # | 前台實際操作 | 實測 | 歸屬 | 換 OSM 之後 |
|---|---|---|---|---|
| 1 | 訂閱付款 | 步驟 3–6 | ResoMap | 走 Apple 內購，與地圖無關。不變 |
| 2 | 搜尋店家 | 步驟 9 | **依賴 Google** | **會變**：台灣小型商家搜不到的比例明顯上升 |
| 3 | 找到店家：帶出店名地址 | 步驟 10 | **依賴 Google** | **會變**：地址常缺門牌或缺里，要讓商家能補 |
| 4 | 建立景點／商家 | 目前沒有 | **目前不存在** | **要新增**：搜不到 → 手動輸入 → 地圖選點 |
| 5 | 選景點類型（一般／商家） | 步驟 12 | ResoMap | 自家商業規則。不變 |
| 6 | 上傳語音檔 | 步驟 11 | ResoMap | 不變 |
| 7 | 上傳導覽配圖 | 步驟 13 | ResoMap | 不變 |
| 8 | 填寫名稱與介紹文案 | 步驟 13–14 | ResoMap | 不變 |
| 9 | 送審 | 步驟 15 | ResoMap | 不變 |
| 10 | 後台審核通過 | 步驟 19 | ResoMap | 不變 |
| 11 | 後台開放認領 → 商家認領 | 步驟 20–21 | ResoMap／待確認 | 綁自家 ID 就不變；綁 `place_id` 要重新對應 |
| 12 | 前台顯示與播放 | 步驟 20b | ResoMap | 由認領狀態決定。不變 |

> 順帶一個發現：**認領是第 11 步，不是第 4 步**——排在上傳、送審、後台審核全部做完之後，跟直覺完全相反。這也是原稽核第 18 步那個死路的來源。

### Google 版真正的問題：新開的店進不來

一家上個月才開的餐廳，想付錢做語音導覽——但他做不到。因為第 2 步是搜 Google，Google 還沒收錄，商家在 ResoMap 搜不到自己，整條付費流程從第 2 步就走不下去。

> **ResoMap 現在的獲客資格，是由 Google 決定的。**

現在進不來的客群：新開幕的店／夜市攤位、市場攤商、路邊小店／改過名的店／搬過家的店／沒有店面的景點（廟宇分殿、私人園區、步道涼亭）／Google 上重複或錯誤的 POI。

### 換 OSM 的好處

1. **可以自己建立地點**——搜不到就當場手動建，把人留住
2. **新開的店當天就能上架**——不用等 Google 審核
3. **資料錯了可以自己修**——不必跟 Google 申訴
4. **沒有查詢配額與費用壓力**——搜尋反而能做得更好用
5. **資料可以合法留在自己手上**——解掉現存的 Google 條款疑慮
6. **商家補的資料變成平台資產**——累積出 Google 沒有的在地 POI 庫

誠實的代價：底圖會比 Google 空、中文標註不完整、公車站等圖層要自己接、導航跳轉沒有對等替代；OSM 採 ODbL，有 share-alike 義務。

### 必須先問到答案的兩題

1. 第 2 步的搜尋框，打的是 Google Places 還是自家景點資料庫？
2. 第 11 步的認領，綁定的是 Google `place_id` 還是自家 ID？

只要這兩題有答案，遷移範圍就能算得出來。

## 稽核方法與界線

- 以真實商家帳號完整走完訂閱至上線流程，逐步截圖記錄。
- 本文只陳述觀察到的流程問題與責任歸屬，**不含修復方案**。
- 地圖評估中標示「待確認」者為截圖無法判讀、需工程師回覆的項目，**未經確認前不應作為決策依據**。
