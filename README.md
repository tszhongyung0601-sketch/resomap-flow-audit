# ResoMap 商家訂閱流程稽核

以商家身分實際走完 ResoMap「訂閱付款 → 語音上線」全流程，共 **21 個步驟**，逐步截圖記錄，並就流程本身指出問題與責任歸屬。

附錄另含一份 **Google Maps → OpenStreetMap 遷移評估**，依同一份實測流程列出所有 Google 觸點與遷移代價。

- **實測日期**：2026/08/26 – 08/27
- **測試景點**：香記烤鴨（台中市南區台中路 252 號）
- **後台**：`backend.resomap.app`（版本 `dev-1.0.0`）
- **線上閱讀**：https://tszhongyung0601-sketch.github.io/resomap-flow-audit/

> **關於截圖內容**：`evidence/` 為實測過程的原始截圖，除了帳號 Email 已塗銷之外未經修改。保留原樣是為了讓每一項發現都可被獨立查核。

## 一句話結論

**付費與交付之間，產品裡沒有任何一條路把它們接起來。**

商家買的是「3 個景點」的上架權，但付款完成的那一刻 App 沒有變化：沒有引導、沒有額度顯示、沒有「我的景點」入口。他必須自己回到地圖、自己打字搜尋店名、自己錄音、自己寫文案、自己拍照，再自己猜到右上角的三個點，最後靠自己反覆回訪去試「認領」按鈕能不能按。整條主線由三個純人工關卡串起來，而商家一個都看不到。

```

  ResoMap-flow-audit.pptx              33 頁簡報（圖文對照，含地圖評估附錄）

  第一步…第二十一步驟*.png/jpg          原始實測截圖 21 張（含後台 2 張）
build/
  deck.js                              簡報產生器（pptxgenjs）
  prep*.js                             截圖裁切／縮放腳本（sharp）
```

`reports/*.html` 為獨立單檔，直接用瀏覽器開啟即可，支援淺色／深色主題。

## 重建簡報

```bash
npm install
node build/prep.js && node build/prep2.js && node build/prep3.js && node build/prep4.js
node build/deck.js
```

`prep*.js` 讀取 `evidence/` 的原始截圖，輸出到 `build/img/`；`deck.js` 讀 `build/img/` 產生 `.pptx`。
若 `build/img/` 已存在（本 repo 已含），可直接跑 `node build/deck.js`。

重建網站（`reports/` 改動後）：

```bash
node build/pages.js
```

> 註：`prep*.js` 目前寫死來源路徑為桌面的「商家訂閱流程2」資料夾。若要在別台機器重跑，需先把路徑改指到本 repo 的 `evidence/`。

## 附錄：Google Maps → OpenStreetMap

完整評估見 `reports/02-map-migration-assessment.html`。

**結論**：如果景點是用 Google 的 `place_id` 當主鍵，這就不是換底圖，是換資料庫。

證據在步驟 9 → 10：商家搜到「香記烤鴨」的當下，這個景點在系統裡還沒有任何語音，卻已經有完整店名與 `40250台灣臺中市南區國光里台中路252號` ——郵遞區號在前、有「里」、國名在前，這是 Google `formatted_address` 的台灣格式，不是使用者手打的。

### 遷移代價分級

- **A 級（直接壞掉，不是犧牲是重做）**：景點主鍵失效／商家搜不到自己的店／地址格式不穩定
- **B 級（明顯降級）**：底圖 POI 變空／中文標註不完整／大眾運輸圖層要自己接／導航跳轉沒有對等替代／照片評分營業時間全無
- **C 級（會變好）**：Places 帳單歸零／解掉現存的 Google 條款風險 — 但 OSM 是 ODbL，有 share-alike 義務

### 必須先問到答案的三題

1. 景點的主鍵是 Google `place_id`，還是自家 UUID？
2. 名稱與地址是存起來，還是每次即時打 API？
3. 搜尋框搜的是 Google Places，還是自家景點資料庫？

沒有這三個答案，任何遷移估算都是猜的。
